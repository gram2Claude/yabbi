# Источник Yabbi — сводка (endpoints, поля, решения)

Единая точка правды по источнику **Yabbi** (`my.yabbi.me`) для проекта `24_yabbi_automate`.
Составлено по разведке живого кабинета рекламодателя **`Igronik_x5`** (X5/5ka), 2026-07-03.

> ⚠️ У Yabbi **нет публичного API**. Данные забираются HTTP-запросами к веб-ЛК по **cookie-сессии**,
> которую выдаёт логин в личный кабинет. Это не REST API — это авторизованный веб-скрейпинг JSON-ответов.

---

## 1. Авторизация (cookie-сессия)

- Форма входа: `POST https://my.yabbi.me/login?method=account`
  - Тело: `application/x-www-form-urlencoded`, поля `login`, `password`.
  - Вкладка **«Рекламодатель»** (не «Агентство»). Капчи/2FA/CSRF-поля в форме нет.
  - ⚠️ **ОБЯЗАТЕЛЬНЫ заголовки** `Referer: https://my.yabbi.me/login?method=account` и
    `Origin: https://my.yabbi.me`. Без них сервер отвечает «Неправильный логин или пароль» (антибот).
- Успех = редирект на `/campaign?method=list` + cookies:
  - `as-account-session` (64 hex, HttpOnly) — сессия,
  - `as-account` (= логин),
  - `csrf` (41 симв.).
- **TTL сессии = 1 час** (`Max-Age=3600`), продлевается на каждый запрос → перелогин при простое >1 ч.
- Учётные данные — в `.env` проекта (`YABBI_LOGIN` / `YABBI_PASSWORD`, gitignored).

## 2. Используемые endpoints

Все — `GET`, ответ — JSON (`Content-Type: text/plain`). Параметры дат — **Unix-время в миллисекундах**
(секунды × 1000). ⚠️ **Сутки Yabbi бакетируются по МОСКОВСКОЙ полуночи** (проверено 2026-07-04:
трафик 21:00–22:00 UTC 30.06 лёг в бакет «2026-07-01»); границы окон передавать полуночами МСК,
не UTC. **`startTime==endTime` возвращает НЕ весь день, а лишь стартовый ~часовой бакет** — день D
забирается окном `[D 00:00 МСК, D+1 00:00 МСК]` с фильтром по ключу/полю дня `== D`.

| Роль | Endpoint | Гранулярность |
|------|----------|---------------|
| Справочник кампаний | `GET /ajax?method=campaign-list&startTime=<ms>&endTime=<ms>&status=all&type=all` | 1 строка на кампанию (уникальна по `id`); метрики в `state` — агрегат за период |
| Статистика по баннерам по дням | `GET /statistics/statistics-per-banners-per-days?startTime=<ms>&endTime=<ms>` | баннер × день |
| Статистика по кампаниям по дням | `GET /report-ajax?method=campaigns-statistics-daily&startTime&endTime&id=<csv id>` | кампания × день (нужны id кампаний) |
| Статистика по баннерам (отчёт) | `GET /report-ajax?method=campaigns-banners-daily&startTime&endTime&id=<csv id>` | баннер × день, с привязкой к кампании (`campaign` id, `url`) |
| Итог по кампаниям | `GET /report-ajax?method=campaigns-statistics&startTime&endTime&id=<csv id>` | кампания (агрегат за период) |

Основные для проекта — **справочник кампаний** и **статистика по баннерам по дням** (последний дал пользователь).

## 3. Какие поля мы получаем

### 3.1. Справочник кампаний (`campaign-list`)

Каждая кампания — объект из **57 полей** (большинство — конфиг таргетинга). Значимые:

**Плоские поля:**

| Поле | Тип | Смысл / пример |
|------|-----|----------------|
| `id` | string | ID кампании (Mongo ObjectId), напр. `699d76aa75a575f6ed87fbbf` |
| `name` | string | Название, напр. `Пятёрочка_Fame to Flame_jul_2026` |
| `type` | string | `rtb` (баннер) / `vast` (видео) |
| `bidType` | string | `click` / `show` — модель оплаты |
| `status` | string | `active` / `stopped` / `paused` |
| `amountIFA` | int | Охват (уникальные пользователи). ⚠️ В `campaign-list` = **0** (не заполняется); брать из `campaigns-statistics` (см. §4). |
| `amountMAC` | int | Охват по MAC (= 0 у этого аккаунта). |
| `owner` | string | ID аккаунта (= accountID кабинета) |
| `group` | string | ID группы кампаний |
| `trafType` | string | Тип трафика (`app`/…) |
| `buyingType` | string | Тип закупки (`evenly`/…) |
| `device` | string | Устройства (`all`/…) |

Плюс `time` (объект: `start`/`end` дат кампании) и вложенный объект **`state`** с метриками.
Прочие поля — конфиг: `calendar`, `geoByLevel`, `strategy`, `ssp`, `publishers`, `kpi`, `limit`,
`segment`, `retargeting`, `brandSafety`, флаги blacklist/whitelist и т. п.

**`state` — метрики кампании (27 полей, агрегат за выбранный период):**

| Поле | Тип | Смысл |
|------|-----|-------|
| `budget` | number (float) | **Расход, ₽** (десятичный; напр. `36178.221`) |
| `win` | int | Показы выигранные |
| `view` | int | Показы/просмотры |
| `load` | int | Загрузки (видимость) |
| `click` | int | Клики |
| `firstQuartile` / `midpoint` / `thirdQuartile` / `complete` | int | Видео: досмотры 25% / 50% / 75% / 100% |
| `start` | int | Старты видео |
| `bid` / `auction` | int | Ставки / аукционы |
| `clickPlus` / `clickExtra` / `clickReached` / `clickWhisla` | int/null | Доп. клики |
| `dayBudget` / `dayClick` / `dayClickPlus` | int | Дневные лимиты/значения |
| `bot` / `mute` / `unmute` / `close` / `appInstall` / `conversion` / `appRevenue` / `show` | int | Прочие события |

> ⚠️ Метрики `state` — **агрегат за период** `startTime…endTime`, не по дням. Разбивка по дням —
> через `campaigns-statistics-daily`.

### 3.2. Статистика по баннерам по дням (`statistics-per-banners-per-days`)

JSON-массив; строка = баннер за день. **Ровно 5 полей:**

| Поле | Тип | Смысл |
|------|-----|-------|
| `day` | string | Дата `YYYY-MM-DD` |
| `URL` | string | Трек-ссылка баннера (идентичность баннера) |
| `show` | int | Показы |
| `click` | int | Клики |
| `complete` | int | Досмотры видео (100%) |

Пустой период → тело `null` (не `[]`).

⚠️ **Денег/расхода, охвата и ID кампании в этом endpoint НЕТ** — только показы/клики/досмотры.
Деньги есть только на уровне кампании (`campaign-list.state.budget`).

**Что зашито в `URL`** (utm/mt-метки, разбираются НЕединообразно):
`utm_campaign` / `mt_campaign` = код медиаплана (напр. `DM000212-009_igronik_media_5ka_rf-syr_05_2026|format_olv|type_true-view`),
`utm_content` / `mt_creative` = креатив/аудитория (`|creo_target`, `|aud_int`), `erid` = маркировка.
Это **код медиаплана**, а не человекочитаемое `name` кампании из справочника; у части ссылок
(напр. `yandex.ru/maps`) utm-меток нет вовсе, только `erid`.

**Как привязать баннер к кампании (ПРОВЕРЕНО 2026-07-03).** Парсить `URL` НЕ годится (код медиаплана ≠ имя
кампании; у yandex.maps-ссылок utm-меток нет вовсе). Надёжный способ — отчёт `campaigns-banners-daily`:
у каждого баннера там есть `url` и `campaign` (id кампании). **Поле `url` посимвольно совпадает с `URL` из
`statistics-per-banners-per-days`** (тест: кампания Перекрёсток — 10 из 10 URL совпали). Цепочка привязки:
`per-banners.URL` → (`campaigns-banners-daily.url`) → `campaign` id → (`campaign-list.id`) → имя/тип/статус.
`campaigns-banners-daily` также несёт `id` (id баннера), `name` (имя креатива) и метрики баннера за день
(в `state`) — то есть может служить и источником баннерных фактов, и мостом привязки.

## 4. Особенности и подводные камни

- **Сутки — по МСК; `[D, D]` — это НЕ «весь день D»** (см. §2). Ошибка 2026-07-03 «endTime включает
  свой день, для одного дня startTime==endTime==D» давала занижение daily-метрик в 15–20 раз и потерю
  кампаний без ночного трафика; исправлено 2026-07-04 (окно `[D, D+1]` МСК + фильтр по дню).
- **Маппинг колонок кабинета («Мои кампании») на `state`: «Показы» = `win`, «Видимость» = `load`,
  «Клики» = `click`, CTR = click/win.** `view` — не «Видимость» (чуть больше `load`). Сверено до
  единицы по 3 кампаниям (2026-07-04).
- **`/report-ajax` (`campaigns-statistics-daily`, `campaigns-statistics`) считает ~5–7 с НА КАМПАНИЮ
  из `id`-списка; скорость плавает день ко дню** (2026-07-03 41 id отвечали <120 c, 2026-07-04 — не
  отвечали и за 300 с; сервер изредка рвёт соединение `10054`). Клиент шлёт id батчами по `ID_CHUNK=5`
  (~30–35 с на батч) и склеивает ответы; `campaigns-banners-daily` быстрый, но батчится единообразно.
- **Справочник период-зависим.** И состав кампаний, и агрегаты в `state` зависят от окна `startTime…endTime`
  (замер: 120 дней → 43 кампании, 400 дней → 55, 1 день → 29). Это НЕ статичный справочник.
- **Охват (`amountIFA`) — только на уровне кампании, источник = `campaigns-statistics` (total).** В `campaign-list`
  он = 0; в `campaigns-statistics-daily` приходит, но **константой по всем дням** (это агрегат кампании, не дневной,
  и не совпадает с total: замер 10166 в daily vs 8688 в total за один период); в баннерных endpoint'ах поля нет.
  Охват = уникальные пользователи → **не суммируется по дням и не бьётся по баннерам**. `amountMAC` = 0 у аккаунта.
- **Фильтр статуса** = параметр `status` (`all` / `active` / `stopped` / `paused`) — задаёт подмножество
  (замер за 120 дней: `active` → 10, `stopped` → 33, `all` → 43).
- **`URL` не уникален** в статистике по баннерам: один и тот же `URL` встречается несколькими строками
  за один `day` (разные баннеры с общей ссылкой) → агрегировать суммированием по `(day, URL)`.
- **Деньги — десятичные** (`state.budget`, float ₽), в отличие от целочисленных денег avito.
- **Сетевой затык >16 КБ (на машине win-vm).** Ответы больше ~16 КБ от `my.yabbi.me` на этой машине
  стопорятся (MTU/MSS на пути; воспроизведено и на статике, и на статистике). **Обход: запрашивать с
  `Accept-Encoding: gzip` и распаковывать** — URL-ы сильно жмутся (35 КБ → 1.9 КБ). Помесячный запрос даже
  в gzip может превысить порог на проводе → тянуть **по дням** и склеивать.

## 5. Зафиксированные решения (по запросам)

Решения пользователя (2026-07-03):

1. **`startTime` запроса = ГЛОБАЛЬНАЯ ДАТА НАЧАЛА** (параметр проекта, аналог avito `TEST_GLOBAL_START_DATE`).
   Справочник кампаний и накопительные запросы стартуют от неё (не от «последних N дней»), чтобы состав и
   агрегаты были полными и стабильными. `endTime` — конец периода (для справочника «на сейчас» — текущая дата).
   **Значение: `YABBI_GLOBAL_START_DATE=2026-06-01`** (в `.env` проекта; задано 2026-07-03).
2. **Фильтр статуса всегда = `all` (Все)** — `status=all` (и `type=all`) в `campaign-list`. Возвращаются
   кампании всех статусов; не фильтровать по active/stopped/paused.

### 5.1. Справочник кампаний — спецификация

- **Основа справочника = `campaign-list`** (выбран потому, что здесь есть тип кампании **видео/баннер**
  `type` = `vast`/`rtb`, и человекочитаемое `name`).
- **Запрос:** `GET /ajax?method=campaign-list&startTime=<глоб. дата начала>&endTime=<вчера>&status=all&type=all`.
  - `startTime` = глобальная дата начала (00:00 МСК); `endTime` = **конец вчерашнего дня МСК**
    (последняя мс дня; не сегодня — сегодняшний день неполный).
- **Обновление:** полная **перезапись** таблицы каждый день (overwrite, не инкремент).
- **Дедупликация обязательна:** уникальность по `id` кампании; дубли удалять по `id` (выживает первая строка).
- **Выходные поля (5):**

| Поле | Тип | Комментарий |
|------|-----|-------------|
| `id` | string | ID кампании (ObjectId). Первичный ключ справочника. |
| `name` | string | Название («Пятёрочка_Fame to Flame_jul_2026»). Человекочитаемое только здесь. |
| `type` | string | `rtb` (баннер) / `vast` (видео). |
| `bidType` | string | Модель оплаты: `click` / `show`. |
| `status` | string | `active` / `stopped` / `paused`. |

  Метрики `state`, охват и конфиг таргетинга в справочник не выносятся (это статичный справочник кампаний).

### 5.2. Статистика по кампаниям по дням — таблица фактов

- **Источник = `campaigns-statistics-daily`** (`/report-ajax`, нужен `id=<csv id кампаний>` из справочника;
  id — батчами по `ID_CHUNK=5`, см. §4).
- **Грань: кампания × день.**
- **Забор: каждый день отдельным запросом — окно `[D 00:00 МСК, D+1 00:00 МСК]`, из ответа берём только
  ключ `D`** (⚠️ `startTime==endTime==D` вернул бы лишь стартовый ~часовой бакет — ошибка, исправленная
  2026-07-04; хвостовой бакет `D+1` отбрасывается фильтром). Диапазон `date_from…date_to`.
- **Колонки:**

| Колонка | Источник | Тип | Комментарий |
|---------|----------|-----|-------------|
| `date` | ключ объекта (`YYYY-MM-DD`) | date | **Дата, за которую статистика** (день метрик). |
| `id` | `id` | string | ID кампании (FK → справочник `campaign-list`). |
| `name` | `name` | string | Имя кампании (денорм. из справочника). |
| `win` | `state.win` | int | **Показы** (= «Показы» в кабинете, сверено до единицы). |
| `load` | `state.load` | int | **Видимость** (= «Видимость» в кабинете; НЕ `view`). |
| `click` | `state.click` | int | Клики (= «Клики» в кабинете). |
| `budget` | `state.budget` | number (float) | Расход, ₽ (десятичный). |
| `bid` | `state.bid` | int | Ставки (участий в торгах). |
| `auction` | `state.auction` | int | Аукционы. |
| `firstQuartile` | `state.firstQuartile` | int | Видео 25% (0 у баннеров, >0 у vast). |
| `midpoint` | `state.midpoint` | int | Видео 50%. |
| `thirdQuartile` | `state.thirdQuartile` | int | Видео 75%. |
| `complete` | `state.complete` | int | Видео 100% (досмотры). |

  `type`/`status`/`owner`/`group` в этом endpoint пустые — при необходимости брать из справочника по `id`.

### 5.3. Статистика по баннерам по дням — таблица фактов

- **Основа = `statistics-per-banners-per-days`** (поля источника: `day`, `URL`, `show`, `click`, `complete`).
- **Забор: окно `[D 00:00 МСК, D+1 00:00 МСК]` + фильтр `day == D`** (окно UTC резало ночь 00:00–03:00 МСК —
  исправлено 2026-07-04; нулевой диапазон метод отвергает `400`).
- **Обязательно добавляем `campaign_id`** — привязка баннера к кампании через `campaigns-banners-daily`
  (`per-banners.URL` == `campaigns-banners-daily.url` → `campaign` id; проверено, совпадает посимвольно).
  Парсинг URL для привязки не используем (у yandex.maps-баннеров utm-меток нет).
- **Агрегация: грань = `date + URL`** (одна строка на баннер-URL за день); дубли `URL` за день
  сворачиваются суммой `show`/`click`/`complete`. `campaign_id` определяется по `URL`.
- **Колонки:**

| Колонка | Источник | Комментарий |
|---------|----------|-------------|
| `date` | `day` | Дата, за которую статистика (грань). |
| `campaign_id` | обогащение: `URL` → `campaigns-banners-daily.campaign` | **ID кампании** (FK → справочник `campaign-list`). |
| `URL` | `URL` | Идентификатор баннера (грань). |
| `show` | Σ `show` | Показы (сумма по `date+URL`). |
| `click` | Σ `click` | Клики (сумма). |
| `complete` | Σ `complete` | Досмотры видео 100% (сумма). |

### 5.4. Охват (накопительный) — таблица фактов

- **Источник = `campaigns-statistics`** (итог по кампаниям): `/report-ajax?method=campaigns-statistics&startTime&endTime&id=<csv id>`.
  Охват = `amountIFA`, **только на уровне кампании**.
- **Охват НЕаддитивен** (уникальные пользователи) — суммировать по дням нельзя (проверено: сумма дневных
  завышает втрое+). Берётся **накопительным итогом**, как «кумулятивная метрика» в avito (`10_template_tz.md` §3.7/§4.N).
- **Забор: на каждый день D из `[глоб. дата начала, вчера]` — отдельный запрос** `campaigns-statistics`
  с `startTime = глоб. дата начала (00:00 МСК)`, `endTime = конец дня D МСК (последняя мс)` →
  `amountIFA` = накопительный охват `[глоб. старт, D]`
  (проверено 2026-07-03: в целом растёт при расширении окна, НО `amountIFA` — оценочная метрика и может
  немного проседать день-к-дню, т.е. `increment` иногда отрицателен — напр. Перекрёсток 07-01 `78469` → 07-02 `75126`,
  increment `−3343`. Это не баг, а свойство модельного охвата Yabbi; клампить к 0 НЕ надо).
- **Грань: кампания × день. Колонки:**

| Колонка | Источник | Комментарий |
|---------|----------|-------------|
| `date` | день D | конец накопительного окна. |
| `campaign_id` | `id` | ID кампании (FK → справочник `campaign-list`). |
| `name` | `name` | имя кампании. |
| `reach` | `amountIFA` за `[глоб. дата начала, D]` | накопительный охват. |
| `increment` | `reach[D] − reach[D−1]` | дневной прирост. Для первого дня ряда: если `date_from` = глоб. дате начала → `increment = reach`; если `date_from` позже → прирост от baseline (`reach` за `date_from−1`). |
